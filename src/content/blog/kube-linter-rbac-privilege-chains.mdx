Four months ago I wrote about a blind spot in Kubernetes RBAC linting: per-object linters cannot see indirect privilege escalation, because the chain from a Deployment through its ServiceAccount to a ClusterRoleBinding spans multiple manifests. I built [kube-chainsaw](https://github.com/ugiordan/kube-chainsaw) to fill the gap, and the advice at the time was to run it alongside kube-linter.

As of last week, that advice is obsolete. The graph analysis merged into [kube-linter](https://github.com/stackrox/kube-linter) itself as the `kube-chainsaw-rbac` check: the analyzer is imported as a library, same pattern kube-linter already uses for kubeconform. One linter, one report, one SARIF file.

This post is the short version of what changed: what the check catches, how to enable it, and what still needs the standalone tool.

## Same manifests, new result

Take the operator setup from the previous post. A ClusterRole with Secret access and RBAC modification rights, a cluster-wide binding, a Deployment using it:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: operator-manager-role
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: ["get", "list", "watch", "create", "update"]
  - apiGroups: ["rbac.authorization.k8s.io"]
    resources: ["clusterrolebindings", "clusterroles"]
    verbs: ["create", "patch", "update"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: operator-binding
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: operator-manager-role
subjects:
  - kind: ServiceAccount
    name: operator-sa
    namespace: operator-system
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: operator-controller
  namespace: operator-system
spec:
  selector:
    matchLabels:
      app: operator
  template:
    metadata:
      labels:
        app: operator
    spec:
      serviceAccountName: operator-sa
      containers:
        - name: manager
          image: operator:latest
```

kube-linter 0.8.3, the latest release, reports six findings on this input: `latest-tag`, `no-read-only-root-fs`, `non-existent-service-account`, `run-as-non-root`, `unset-cpu-requirements`, `unset-memory-requirements`. All valid, all hygiene. The escalation chain is invisible, same as in July.

With the check enabled, the picture changes:

```bash
kube-linter lint operator.yaml --include kube-chainsaw-rbac
```

```
operator.yaml: (object: <no namespace>/operator-manager-role rbac.authorization.k8s.io/v1, Kind=ClusterRole) [HIGH] Secrets access: Role "operator-manager-role" grants access to dangerous resource "secrets" (check: kube-chainsaw-rbac, remediation: Restrict secrets access to specific namespaces and only the verbs needed)

operator.yaml: (object: <no namespace>/operator-manager-role rbac.authorization.k8s.io/v1, Kind=ClusterRole) [HIGH] RBAC modification capability: Role "operator-manager-role" grants access to dangerous resource "clusterrolebindings" (check: kube-chainsaw-rbac, remediation: Limit RBAC modification to dedicated admin roles with proper audit)

operator.yaml: (object: <no namespace>/operator-manager-role rbac.authorization.k8s.io/v1, Kind=ClusterRole) [HIGH] Privilege escalation via role/binding modification: Role "operator-manager-role" can create/modify roles or bindings (privilege escalation risk) (check: kube-chainsaw-rbac, remediation: Restrict ability to create/modify roles and bindings to admin users only)
```

The three findings that matter are the ones that were missing: secrets access, RBAC modification, and the combination that lets this operator grant itself `cluster-admin` at runtime. Severity still comes from binding scope, so the same role bound with a namespace-scoped RoleBinding reports WARNING instead of HIGH.

## Enabling the check

The change [merged into main](https://github.com/stackrox/kube-linter/pull/1216) and ships in the next release. Until that release is cut, build from source: `go install golang.stackrox.io/kube-linter/cmd/kube-linter@main`.

The check is opt-in, so nothing changes for existing users until you ask for it:

```bash
kube-linter lint config/ --include kube-chainsaw-rbac
```

Or in the config file, alongside the checks you already run:

```yaml
checks:
  include:
    - kube-chainsaw-rbac
```

The parameters from the standalone tool are available by defining a custom check on the same template:

```yaml
customChecks:
  - name: kube-chainsaw-rbac-tuned
    template: kube-chainsaw
    params:
      rules:            # only these rule IDs, empty means all supported
        - KC-013
      minSeverity: high # drop info and warning findings
      suppressionsFile: suppressions.yaml
```

The suppressions file format is unchanged from the standalone tool:

```yaml
suppressions:
  - rule_id: KC-006
    resource_name: operator-manager-role
    reason: "Operator manages TLS certificates stored as Secrets"
```

## What's new since July

Two things landed during the upstream review that even standalone kube-chainsaw users did not have in July.

**Group identities.** Every service account receives grants not only through direct ServiceAccount subjects, but also through its implicit identities: the `system:serviceaccounts:<namespace>` group, the `system:serviceaccounts` group, `system:authenticated`, and its user name `system:serviceaccount:<namespace>:<name>`. A binding to any of those now links the workload to the role:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: batch-job
  namespace: default
spec:
  serviceAccountName: app-sa
  containers:
    - name: job
      image: busybox:1.36
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: legacy-grant
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
  - kind: Group
    name: system:serviceaccounts:default
```

```
group-binding.yaml: (object: default/batch-job /v1, Kind=Pod) [CRITICAL] Pod running with cluster-admin privileges: Pod "batch-job" uses ServiceAccount "default/app-sa" which is bound to cluster-admin via ClusterRoleBinding "legacy-grant" (check: kube-chainsaw-rbac, remediation: Never use cluster-admin for pod service accounts; create a scoped role)
```

This slipped through the July version of kube-chainsaw too. It was found during the review and fixed in [v1.1.2](https://github.com/ugiordan/kube-chainsaw/releases/tag/v1.1.2).

**Severity in SARIF.** kube-linter diagnostics now carry severity and metadata, so SARIF output maps findings to `error`, `warning`, and `note` levels, attaches the rule ID, remediation, and fingerprint as properties, and emits partial fingerprints for deduplication:

```json
{
  "ruleId": "kube-chainsaw-rbac",
  "level": "error",
  "message": {
    "text": "Secrets access: Role \"operator-manager-role\" grants access to dangerous resource \"secrets\""
  },
  "properties": {
    "rule_id": "KC-006",
    "fingerprint": "a5c1516c...",
    "remediation": "Restrict secrets access to specific namespaces and only the verbs needed"
  },
  "partialFingerprints": {
    "primaryLocationLineHash": "a5c1516c..."
  }
}
```

GitHub Code Scanning finally triages these results by severity instead of showing them as a flat list.

## One linter, one report

If you followed the July setup, your CI runs two tools: kube-linter for manifest hygiene, kube-chainsaw for RBAC chains, two SARIF uploads. That collapses into one job:

```yaml
- run: kube-linter lint config/ --include kube-chainsaw-rbac --format sarif --output results.sarif
- uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: results.sarif
```

One command, one report, one upload. Delete the second job unless you need the parts below.

## What stays in kube-chainsaw

Honest scope: the integration covers the RBAC and workload rules, 23 of the 31. Rules that analyze NetworkPolicy, OpenShift SecurityContextConstraints, external exposure, or Secret manifests are rejected at configuration time, because the adapter does not load those kinds. Live cluster scanning with `--from-cluster` also stays standalone. If you need those, keep the standalone tool. For RBAC privilege chains, kube-linter now covers it.

## How it got there

The version that merged is meaningfully better than the one I opened in July, and most of that is the review. The rounds on the pull request caught real gaps: objects whose omitted namespaces default silently, duplicate resource identities overwriting each other, grants through service account groups, rule selections that could never fire because their input kinds are not loaded. Every finding came with a failing test, which is the best kind of review. Credit where it is due: janisz drove most of that hardening.

One engineering note worth keeping: kube-chainsaw's analyzer package has no dependencies outside the standard library, so importing it into kube-linter added nothing to kube-linter's dependency tree. That constraint is what made the integration a two-file conversation instead of a dependency negotiation.

The blind spot from July is closed where it matters most, inside the linter people already run. Enable the check, delete the second CI job, and point your SARIF upload at one file.
