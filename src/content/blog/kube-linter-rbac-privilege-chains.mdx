The [previous post](https://ugiordan.dev/blog/rbac-privilege-chains/) covered why per-object RBAC linting misses indirect privilege escalation: the chain from a Deployment through its ServiceAccount to a ClusterRoleBinding spans multiple manifests, and a linter that reads one object at a time cannot correlate them. The fix at the time was kube-chainsaw, a standalone tool run alongside kube-linter.

That analysis now runs inside kube-linter itself, as the `kube-chainsaw-rbac` check. This post is the technical walkthrough: the analysis model, the rule set, how service account identities are resolved, what the SARIF output carries, and every knob for configuring it.

## The detection gap

Here is the reference input, carried over from the previous post. Three ordinary manifests: a ClusterRole with Secret access and RBAC modification rights, a cluster-wide binding, and a Deployment using it.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: operator-manager-role
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: ["get", "list", "watch", "create", "update"]
  - apiGroups: ["rbac.authorization.k8s.io"]
    resources: ["clusterrolebindings", "clusterroles"]
    verbs: ["create", "patch", "update"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: operator-binding
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: operator-manager-role
subjects:
  - kind: ServiceAccount
    name: operator-sa
    namespace: operator-system
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: operator-controller
  namespace: operator-system
spec:
  selector:
    matchLabels:
      app: operator
  template:
    metadata:
      labels:
        app: operator
    spec:
      serviceAccountName: operator-sa
      containers:
        - name: manager
          image: operator:latest
```

Per-object checks report six findings on this input: `latest-tag`, `no-read-only-root-fs`, `non-existent-service-account`, `run-as-non-root`, `unset-cpu-requirements`, and `unset-memory-requirements`. All valid, all hygiene. Nothing about the fact that this operator can create ClusterRoleBindings and is bound cluster-wide, which means it can grant itself `cluster-admin` at runtime. That fact lives in the correlation between three manifests, not in any one of them.

## How the analysis works

The check converts every loaded object into a permission graph:

```
workload -> service account -> binding -> role -> verbs/resources
```

Nodes are the RBAC and workload objects kube-linter already parsed. Edges are the references between them: a pod spec's `serviceAccountName`, a binding's `subjects`, a binding's `roleRef`. Rules then evaluate the graph in two passes: per-role checks on the rule sets (wildcards, dangerous verbs, sensitive resources, escalation combinations), and path checks that walk from a workload through its service account and bindings to the referenced role (privilege chains, cluster-admin detection).

Severity is a function of binding scope, not just rule content:

| Binding | Wildcards | Severity | Rationale |
|---------|-----------|----------|-----------|
| ClusterRoleBinding | yes | CRITICAL | full cluster access |
| ClusterRoleBinding | no | HIGH | broad but scoped access |
| RoleBinding | yes | HIGH | namespace-wide access |
| RoleBinding | no | WARNING | limited blast radius |
| none (unbound role) | | INFO | dormant template |

The same ClusterRole therefore produces different severities depending on how it is bound, which is a distinction no per-object check can make: it requires correlating the role with its bindings.

All rule matching is apiGroup-aware. A CRD named `secrets` in the `custom.example.com` group does not trigger the secrets-access rule, because the rule matches `secrets` in the core API group only.

## The rule set

The integration covers 23 of kube-chainsaw's 31 rules: everything that operates on RBAC objects, workload pod specs, or the graph itself.

| Category | Rules | In kube-linter |
|----------|-------|----------------|
| Wildcard permissions | KC-001, KC-002 | yes |
| Dangerous verbs (escalate, impersonate, bind) | KC-003 to KC-005 | yes |
| Sensitive resources (secrets, pods/exec, nodes, PVs, RBAC objects) | KC-006 to KC-010 | yes |
| Escalation combinations | KC-011, KC-012 | yes |
| Privilege chains (cluster-admin pods, RoleBinding to ClusterRole) | KC-013, KC-014 | yes |
| Aggregated ClusterRoles | KC-015 | yes |
| NetworkPolicy RBAC access | KC-016 | yes |
| NetworkPolicy object analysis | KC-017, KC-018 | standalone only |
| Workload security (privileged, host namespaces, hostPath, capabilities) | KC-019 to KC-022 | yes |
| SCC use permission | KC-023 | yes |
| SCC object analysis | KC-024 | standalone only |
| External exposure (Services, Routes) | KC-025 to KC-027 | standalone only |
| Secret object analysis | KC-028, KC-029 | standalone only |
| Token and CSR access rules | KC-030, KC-031 | yes |

## Identity resolution

The naive version of chain matching compares a binding subject against the workload's service account name and namespace. That misses half of how Kubernetes actually grants permissions, because every service account implicitly holds a set of identities beyond its direct subject:

- the group `system:serviceaccounts:<namespace>`, scoped to all service accounts in one namespace
- the group `system:serviceaccounts`, all service accounts in the cluster
- the group `system:authenticated`, every authenticated principal
- the user name `system:serviceaccount:<namespace>:<name>`, the service account itself

The matcher resolves all of them. A binding to `system:serviceaccounts:default` grants to every service account in `default`, so any workload there running with any service account inherits it:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: batch-job
  namespace: default
spec:
  serviceAccountName: app-sa
  containers:
    - name: job
      image: busybox:1.36
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: legacy-grant
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
  - kind: Group
    name: system:serviceaccounts:default
```

```
group-binding.yaml: (object: default/batch-job /v1, Kind=Pod) [CRITICAL] Pod running with cluster-admin privileges: Pod "batch-job" uses ServiceAccount "default/app-sa" which is bound to cluster-admin via ClusterRoleBinding "legacy-grant" (check: kube-chainsaw-rbac, remediation: Never use cluster-admin for pod service accounts; create a scoped role)
```

## Severity and fingerprints in SARIF

kube-linter diagnostics now carry severity and metadata, and the SARIF formatter maps them onto the levels code scanning platforms understand:

| Diagnostic severity | SARIF level |
|---------------------|-------------|
| critical, high | error |
| warning | warning |
| info | note |

Each result also carries a properties bag with the rule ID, the per-finding remediation, and a fingerprint. The fingerprint is a SHA-256 hash over the rule ID, resource kind, resource name, and resource namespace, deliberately excluding the file path so it stays stable across checkout locations. It is emitted as `partialFingerprints.primaryLocationLineHash`, which GitHub Code Scanning uses to deduplicate results across runs:

```json
{
  "ruleId": "kube-chainsaw-rbac",
  "level": "error",
  "properties": {
    "rule_id": "KC-006",
    "fingerprint": "a5c1516c...",
    "remediation": "Restrict secrets access to specific namespaces and only the verbs needed"
  },
  "partialFingerprints": {
    "primaryLocationLineHash": "a5c1516c..."
  }
}
```

## Enabling the check

The check is opt-in, so existing pipelines keep their behavior until you ask for it.

Get a version with the check (it shipped in kube-linter vX.Y; until that release is cut, build from source with `go install golang.stackrox.io/kube-linter/cmd/kube-linter@latest`):

```bash
kube-linter lint config/ --include kube-chainsaw-rbac
```

Or add it to the checks you already run in your config file:

```yaml
checks:
  include:
    - kube-chainsaw-rbac
```

## Tuning and configuration contracts

The parameters from the standalone tool are available by defining a custom check on the same template:

```yaml
customChecks:
  - name: kube-chainsaw-rbac-tuned
    template: kube-chainsaw
    params:
      rules:            # only these rule IDs, empty means all supported
        - KC-013
      minSeverity: high # drop info and warning findings
      suppressionsFile: suppressions.yaml
```

The suppressions file format is unchanged from the standalone tool:

```yaml
suppressions:
  - rule_id: KC-006
    resource_name: operator-manager-role
    reason: "Operator manages TLS certificates stored as Secrets"
```

Beyond tuning, the check enforces a set of configuration and input contracts designed to fail loudly instead of silently:

- Selecting a rule whose input kinds the integration does not load (KC-017, KC-018, KC-024 to KC-029) fails at configuration time with the missing kinds named in the error. A rule selection that can never produce findings is a configuration error, not a no-op.
- Omitted namespaces normalize to `default` for namespaced kinds, matching API server semantics, and stay empty for cluster-scoped kinds. Finding-to-object attribution normalizes identically, so a pod declared without a namespace matches findings reported against `default/<name>`.
- The deprecated `spec.serviceAccount` field is honored alongside `serviceAccountName`, matching the API server.
- Duplicate resource identities, the same kind, name, and namespace defined in two files, fail conversion with both file paths in the error. Without this, the last definition would silently win and findings could be attributed to the wrong file.
- Conversion failures are reported once per run as a warning diagnostic attributed to the object that triggered the analysis, instead of repeating per object or disappearing entirely.

## One linter, one report

If you followed the previous post's setup, your pipeline runs two tools with two SARIF uploads. That collapses into one job:

```yaml
- run: kube-linter lint config/ --include kube-chainsaw-rbac --format sarif --output results.sarif
- uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: results.sarif
```

The scope caveat: NetworkPolicy object analysis, OpenShift SecurityContextConstraints analysis, external exposure, Secret object analysis, and live-cluster scanning stay in standalone kube-chainsaw. For RBAC privilege chains, kube-linter now covers it.

## Wrap up

Run the reference manifests through the check to see the delta on your own configs:

```bash
kube-linter lint operator.yaml --include kube-chainsaw-rbac
```

```
operator.yaml: (object: <no namespace>/operator-manager-role rbac.authorization.k8s.io/v1, Kind=ClusterRole) [HIGH] Secrets access: Role "operator-manager-role" grants access to dangerous resource "secrets" (check: kube-chainsaw-rbac, remediation: Restrict secrets access to specific namespaces and only the verbs needed)

operator.yaml: (object: <no namespace>/operator-manager-role rbac.authorization.k8s.io/v1, Kind=ClusterRole) [HIGH] RBAC modification capability: Role "operator-manager-role" grants access to dangerous resource "clusterrolebindings" (check: kube-chainsaw-rbac, remediation: Limit RBAC modification to dedicated admin roles with proper audit)

operator.yaml: (object: <no namespace>/operator-manager-role rbac.authorization.k8s.io/v1, Kind=ClusterRole) [HIGH] Privilege escalation via role/binding modification: Role "operator-manager-role" can create/modify roles or bindings (privilege escalation risk) (check: kube-chainsaw-rbac, remediation: Restrict ability to create/modify roles and bindings to admin users only)
```

Enable the check, point your SARIF upload at one file, and delete the second CI job.
